# AP040X2 audit: implementation vs doc/ specs and AP040_IMPLEMENTATION_PLAN.md

Date: 2026-08-16, branch ap040x2, working tree (includes the uncommitted
X2.2 fetch-queue diff to ap040_core.v).  Read-only audit: RTL and tests
were compared against AP040_IMPLEMENTATION_PLAN.md and the manuals in
doc/ (MC68040UM/UMAD, M68000PRM); spec claims below were verified against
the extracted UM text, with WinUAE-oracle conventions respected where the
project has recorded them as authoritative.  Line numbers refer to the
working tree as of this date.

Overall judgment: the architecture-visible core (MOVEC map, frame
formats, SSW/writeback fields, RTE validation, MMU translation/walk/
PTEST/PFLUSH, FPU datatype and trap model) audits clean against the UM
to an unusual degree -- most of what the plan calls "central design
items" is verifiably right, with file:line evidence collected below.
The real defects cluster in four places: interrupt-hold retargeting,
the FPU pending-exception/FRESTORE lifecycle, the FMOVE-out enabled-trap
path, and the X2.1 secondary-lane byte-write/DQM contradiction.  The
plan document itself is stale in several load-bearing places (P1 most
seriously: its STATUS paragraph describes the opposite of the tree).

## 1. Bugs in the ACTIVE configuration
============================================================================

### 1.1 [BUG] irq_hold_lvl can retarget the hold to a never-qualified level

rtl/ap040/ap040_core.v:178-196.  Capture correctly requires
`irq_lvl > sr[10:8]`, but the 45c4eb4f downward-tracking branch is
unconditional: `else if (irq_hold_lvl > irq_lvl) irq_hold_lvl <= irq_lvl;`.
Inside a level-3 handler (mask=3), a level-5 request qualifies (hold=5);
the level-5 source is then cleared while a level-3 request stays asserted:
hold tracks 5 -> 3 and `irq_pend` fires a level-3 interrupt AT the mask.
UM 8.2.6/Table 8-3: only levels strictly above the mask may be taken.
This is exactly the multi-source shape Paula produces.  Fix shape: in the
downward branch, requalify -- `irq_hold_lvl <= (irq_lvl > sr[10:8]) ?
irq_lvl : 3'd0;` (keeps the mask-raise survival for constant pins that
test 136 covers).  Note the dead `rte_irq_*` wires (core.v:596-604)
replicate the same logic and would inherit the bug if ever revived.

### 1.2 [BUG] FMOVE FPn,<ea> never delivers enabled arithmetic exceptions

rtl/ap040/ap040_fpu.v: `exc_req` is asserted only in F_WB (line 1504) and
the store pipeline never reaches F_WB.  Every store completion asserts
`done` with no `fpsr[15:8] & fpcr[15:8]` check: X/S/D/NaN/inf exits in
F_SRC (567, 586, 621, 640, 673, 707), integer stores in F_PACKI (1652),
denormal S/D packing in F_PACKS (1743).  The core's S_FPU_GO checks
fpu_exc_req (ap040_core.v:3626) but it is never raised for r_op==7'h7F.
UM ch.9: FMOVE-out is an arithmetic instruction; enabled OPERR (integer
overflow), SNAN, OVFL, UNFL, INEX2 must trap post-instruction (format $3
for memory destinations, vectors 49-54).  The FPSR status/accrued bits
are set correctly but no trap is taken, and the next dispatch clears the
status byte (fpu.v:488).  The enabled-arithmetic store cases (E49-E54)
appear untested by the corpus slices run so far.

### 1.3 [BUG] Reset and FRESTORE-of-NULL leave FP0-FP7 with wrong contents

ap040_fpu.v:417-419 (reset zeroes fr_s/fr_e/fr_m -> registers read +0.0)
and 450-454 (`fp_reset` from FRESTORE NULL clears FPCR/FPSR/FPIAR but not
the data registers).  UM reset state: FP0-FP7 = nonsignaling NaN ($7FFF,
all-ones mantissa); FRESTORE of NULL returns the FPU to reset state.
Consequence: an OS initializing a task's FP context with FRESTORE #NULL
leaks the previous task's FP register values.

### 1.4 [BUG] FRESTORE neither reports nor clears a pending deferred exception

ap040_core.v:3184-3186: S_FREST1 waits for fpu_bg but ignores
fpu_pend_exc, which is cleared only at hardware reset (1598) or delivery.
A stale F1-deferred exception survives FRESTORE #NULL and fires
pre-instruction on the NEW context's first FPU instruction -- with FPIAR
already zeroed, so the handler cannot identify a faulting instruction.
On a real 040 every FP instruction except FSAVE reports the pending
exception and FRESTORE replaces pending state wholesale.  Together with
1.5 this makes pending-exception state unsound across context switches.

### 1.5 [DIVERGENCE] FSAVE traps a pending deferred exception instead of saving it

ap040_core.v:3152-3155: S_FSAVE1 delivers fpu_pend_exc as a trap.  The UM
makes FSAVE the ONE FP instruction that does not report a pending
exception -- it writes the exception state (BUSY frame) for the handler.
Here a context-switch FSAVE traps in scheduler context, and the FP
exception handler's own FSAVE then sees IDLE, not BUSY.  This is the
documented no-BUSY-frame gap (ap040_fpu.v:19-20, ap040_core.v:5341-5344);
recorded here because the plan's F1 section calls FSAVE merely a "sync
point" without recording this consequence.

### 1.6 [GAP, known-open, confirmed] Interrupt does not outrank privilege violation

ap040_core.v:1481-1485: go_priv raises vector 8 unconditionally; no
irq_pend check exists in S_DECODE.  Matches CODEX_HANDOFF.md:32-36 (fix
prototyped, backed out, to be re-landed with its directed test on ap040
first).  This is the cputest irq/all ANDSR.W round-1 failure.

### 1.7 [RISK] MOVEM restart hole: base register loaded mid-loop

ap040_core.v:2831-2835 (S_MOVEM_LD writes each loaded register
immediately; base An written only at the end, 2790-2793; u_rec rollback
unused for MOVEM).  `MOVEM.L (A0)+,A0-A1` (or control-mode with the base
early in the list): a fault on a later transfer restarts with A0 already
overwritten by loaded data -- the restart recomputes the EA from garbage.
The real 040 continues MOVEM via the format-$7 EA precisely because
restart is unsafe here (UM 8.2.1, 8.4.6.7).  Pure restart is
plan-sanctioned (X2.3), but this case silently corrupts rather than being
merely slow, and a demand-paged OS (the NetBSD milestone) can reach it.
Cheapest fix within the restart model: defer the base-register (and any
register that feeds the EA) update to commit, or roll it back via u_rec.

### 1.8 [DIVERGENCE] Trace vs interrupt priority: UM disagrees, and the two boundary paths disagree with each other

fetch_next (core.v:1447-1463) takes a pending interrupt BEFORE a pending
T1/T0 trace (the completed instruction's trace event is lost, T bits
merely survive in the stacked SR); go_pc (1493-1498) checks tr_t1 BEFORE
irq_pend.  UM Table 8-4 puts Trace (6) above Interrupt (8): trace stacks
first, interrupt on top.  The comment at 1441-1446 says the IRQ-first
ordering is corpus-visible, so this is not called a bug outright -- but
straight-line and taken-branch boundaries currently implement OPPOSITE
orderings, and the corpus may contain no simultaneous T1+IRQ case.
Directed test wanted before X2.3 rearranges boundaries.

## 2. X2.1 sdram32_ctrl (committed, pre-integration)
============================================================================

The deliverable-gate numbers are real: the bench was independently
rebuilt and re-run during this audit -- ALL TESTS PASSED, lockstep clean
on all 2018 checked cycles, fill latency 15 clk_114 dual / 31 fallback,
and all three deliberate breaks reproduce the commit's exact error counts
(2450 / 5214 / 536, incl. the 5a50beef signature).

### 2.1 [BUG] Secondary-lane byte writes depend on a DQM pin the io-board does not route

rtl/sdram32_ctrl.v:65-69 states the premise (SDRAM2 has no DQM;
sys/sys_dual_sdram.tcl:4-41 confirms -- no DQM, no CKE), and nCS
whole-slot masking correctly handles LANE granularity.  But byte writes
to an even word (addr[1]=0, secondary lane) still drive per-byte masks on
sd2_dqm (sdram32_ctrl.v:859, 878, 964), which physically goes nowhere.
With DQM strapped low (required for reads), every byte-granular write to
an even word writes BOTH bytes of the secondary chip, clobbering the
partner byte.  tb_sdram32.v:337 connects the phantom pin to the model, so
the gate's byte-write test (tb line 923, word 0x202 upper-byte) passes in
sim and cannot pass on hardware.  Needs read-modify-write for
secondary-lane byte writes (or evidence the board routes DQM) BEFORE
X2.1b integration.

### 2.2 [GAP] Runtime fallback probe absent

Plan X2.1: "runtime detectable: probe pattern on SDRAM2 at init; config
error out."  Nothing exists; DUAL_SDRAM is compile-time only
(sdram32_ctrl.v:124-128).  A DUAL build on a single-module board would
silently read a floating upper lane.

### 2.3 [GAP] tb_sdram32 not in run_tests.sh; break modes not regression-runnable

The three deliberate breaks were one-off manual edits recorded only in
the commit message -- no plusargs/parameters exist to re-run them.
run_tests.sh has no tb_sdram32 leg, so X2.8's "green at every commit"
does not cover the new controller.  Recommend plusarg-selectable break
modes and a run_tests.sh leg.

### 2.4 [DIVERGENCE] Command engine copied, not instantiated

Plan says "instantiating the proven sdram_ctrl command engine once";
sdram32_ctrl.v is a forked copy (header admits it, lines 31-37) and
sdram_ctrl.v stays in the build -- every future sdram_ctrl fix must be
mirrored by hand.  The diff against the original confirms slot machine,
refresh, write buffer and walker discipline are line-for-line intact;
deltas are exactly the documented ones.

### 2.5 [RISK] Dual-read second CAS shrinks turnaround/precharge margin

Dual chip/cache read slots issue READ2-with-autoprecharge two states
after READ1 (sdram32_ctrl.v:932-944): the discarded 4th beat lands at the
next slot boundary, DQ release ~1 state (~8.7 ns) before a next-slot
write drives (vs 3 states in sdram_ctrl), and internal precharge starts
2 sd_clk later (tRP = 2 sd_clk = 35 ns -- fine for datasheet parts, one
cycle less margin than proven silicon behavior).  The behavioral model
checks neither tHZ nor tRP, so only hardware bring-up can see this.

### 2.6 [RISK] "Width doubled" holds for reads/fills only

The new 32-bit port is read-only line fill (fill_*, sdram32_ctrl.v:193-
201); cpuWR and the write buffer stay 16-bit (a 32-bit store = two
lane-masked slots).  Fine for the T2 gate; the X2.7 internal-cache
replacement gets no store-bandwidth help from X2.1 as it stands.

Verified OK: lockstep structural copies + every-cycle tb identity check;
chipset lane routing by addr[1] for reads AND writes with cycle-identity
against sdram_ctrl on shared stimulus; nCS masking spans ACTIVE through
precharge and exists only in the two 16-bit write arms (reads, refresh,
init never mask -- both chips get AUTO REFRESH and mode-register loads);
single clock domain, no new CDC; walker/snoop ports intact and
eq-checked; 15/31 clk_114 latencies consistent with the state machine
(the plan's "8 clk_114 impossible" floor argument is arithmetically
correct).  X2.1b integration confirmed not started (Minimig.sv:425 still
instantiates sdram_ctrl; no qsf/qip references) -- as the commit states.

## 3. X2.2 fetch queue (uncommitted working-tree diff)
============================================================================

The 437-line diff is a complete implementation of the planned queue: the
epf ring (4 longwords) becomes free-running, filled by a fill engine
whenever the port is idle (ap040_core.v:~5445-5505), drained by
S_FETCH/S_IMMF as pure poppers with a same-cycle bus-forward path;
longword immediates consumed in one pass; flushes on exception entry,
interrupt recognition, MOVEC/PTEST/PFLUSH/CINV/STOP/RESET/HALT, redirect
mismatch, and S-bit change; prefetch is page-guarded (`epf_ftail[31:12]
== pc[31:12]`, conservative for 8K pages, so safe); speculative-fetch
faults recorded in epf_err and re-taken only at the demand point;
killed-fetch faults discarded.  The working tree is suite-green (all
build/*.log ALL TESTS PASSED) and 32 cputest flow-control slices pass
with 0 mismatches.  tb_dat_replay.v's uncommitted change is the matching
harness fix (inject_state clears epf_count/epf_armed).  Exposures:

### 3.1 [RISK] Locked-RMW indivisibility broken at the core/adapter boundary

The fill engine's exclusion list (~5498-5500) does not test lk_cyc
(core.v:627).  CAS/CAS2/TAS intermediate compare states are neither
excluded nor port-idle-free, so a background fetch can be issued between
the locked read and locked write: the bus sees R(locked)-FETCH-W(locked),
violating plan section 8's "locked transfers remain indivisible".  Low
practical impact on this fabric (no agent honors CPU-port lock), but it
is a new contract deviation; adding `!lk_cyc` to the self-fill condition
restores it.

### 3.2 [RISK] Self-modifying-code coherence of the queue -- the fetchbuffer failure class

The queue runs up to 16 bytes ahead continuously; no path compares store
addresses against epf_next..epf_ftail and stores do not flush.  Strictly
040-accurate (SMC requires CPUSH/CINV, and CINV flushes the queue), but
rtl/ap040/experimental/README records the previous fetch-buffered core
"booted DiagROM but not AmigaOS on hardware (sim boots both)" -- exactly
this hazard class, invisible to the suite (t_cache's SMC test uses CINV).
Hardware validation is the only closure; a queue-vs-store address snoop
would be cheap insurance.

### 3.3 [GAP] X2.8 discipline not yet met for the diff

No directed tests seen-to-fail cover the new deferral (epf_err), discard
(epf_kill), or data-op-vs-pending-fetch hold paths (epf_err is reachable
essentially only via berr injection on a speculative fetch, since the
page guard rules out translation differences).  No occupancy measurement
exists: the X2.2 gate is S_FETCH+S_IMMF < 20% on t_integer, cycle claims
must come from the tb_prof histogram, and no tb_prof is in the tree.

### 3.4 [RISK] The occupancy gate can read as met while wall clock does not move

cpu_wrapper.v:267 (`clkena_in = ~cpu_req | bus_complete | bus_berr`) and
the ce-gated core block mean any background fetch stalls the WHOLE core
until it completes: bus wait migrates out of S_FETCH/S_IMMF into whatever
state was running.  Until the fetch port decouples onto the X2.1 32-bit
bus, measure wall-clock cycles alongside occupancy.

### 3.5 [RISK] exception_prefetch assumes no pending queue fetch, two states from its enforcement

core.v:~1207-1225 issues the first vector-stream word unconditionally;
today unreachable with epf_pend set (S_EXC0 waits at ~2436), but the
invariant is remote from its enforcement.  An assertion or explicit pend
check would survive future resequencing.

## 4. Plan document staleness (plan says X, tree does not-X)
============================================================================

### 4.1 P1 STATUS is inverted -- the most misleading text in the plan

Plan lines 669-671 claim "DONE and enabled.  ap040_cache is the only
cache in the system; both cpu_cache_new instances are built without their
storage (CPU_CACHE 0)".  The tree: cpu_wrapper.v:258 sets
AP040_ENABLE_CACHE(0) ("Internal caches OFF: they do not fit this device
with usable timing", 248-257); Minimig.sv:425 and :477 instantiate
sdram_ctrl/ddram_ctrl with CPU_CACHE(1); Minimig.sv:418-424 documents the
revert (measured slower; snoop CDC loses events while clkena frozen).
X2.7/X2.8 already reflect the revert -- only the P1 paragraph was never
corrected.  P1's fit table (internal cache 609 ALMs SMALLER) and the
cpu_wrapper comment (over capacity, -0.716 ns) also flatly contradict
each other; per the X2.8 evidence rule the revert is the trusted state.

### 4.2 P1's "no snoop port" consequence paragraph is stale the other way

Plan 699-704 says ap040_cache has no snoop port so chip RAM is uncached.
RTL: the snoop port exists (ap040_cache.v:62-68), chip RAM is in the
cacheable windows because of it (ap040_tg68k_compat.v:252-261), and
sdram_ctrl exports snoop_tgl/snoop_addr (sdram_ctrl.v:66-71,164-176)
crossed in cpu_wrapper.v:230-245.

### 4.3 F0 text understates the shipped divide/sqrt

Plan F0 says 2 bits/digits per cycle (~41/~40 cycles); the RTL is 3 per
cycle (ap040_fpu.v:1291-1333, 1335-1366 -- the "follow-up headroom" item
already done; X2.5's preamble numbers match the RTL, F0's do not).  The
F_MULT half of F0 is exact as written (single registered 64x64 product,
fpu.v:1286).

### 4.4 Sections 1/4/5 wrapper text superseded by the AP040-only baseline

No CPU mux exists (cpu_wrapper.v:177-200); ap040_tg68k_compat is the only
CPU; fx68k/tg68k removed at 8a0c72b4 by design.  Nothing dangles, but
cpucfg[0] now has NO reader anywhere -- a dead OSD bit (former 68000/010
select).  cpucfg[1] retains meaning (turbochip/turbokick, autoconfig,
ide_fast, cpu_type for ram_cs_guard).  Planned sideband left open at the
wrapper: .fc(), mmu_addr_log/phys, cache burst ports
(cpu_wrapper.v:289-312) -- consistent with the walker-channel
architecture; the section-5 signal list is stale.  Section 4's port list
is implemented with benign extensions (parameters, snoop/window ports,
nmi_ack_toggle, cache_maint_*).

### 4.5 Section 11 continuation text superseded by X2.3 (documented, consistent)

The $7 generator never sets CP/CU/CT/CM (aer_ssw, core.v:1393-1402) and
RTE $7 pops 60 bytes without reading them (2568-2574) -- consistent with
X2.3's "format $7 stays synthetic".  A handler that SETS a continuation
bit is silently ignored; acceptable until X2.6 revisits real writebacks.

### 4.6 Format $4 recognized, never generated

RTE accepts $4 only when AP040_HAS_FPU==0 (core.v:2557-2566, correct both
ways) and the stacking path exists, but no exc() call passes fmt 4: with
FPU disabled, F-line takes vector 11 format $0 (5317-5318) instead of the
LC040 $4 frame (EA + faulted PC) plan section 12 stage 1 requires.  Only
matters for a future LC040 build config; the core header's "$4" claim
overstates.

### 4.7 Section 13's copyback tests: feature deliberately absent

Write-through-with-invalidate only; copyback deferred by plan 385-387 and
X2.7 re-plans it on the 32-bit bus.  Stale as a checklist item, not a
test omission.

## 5. Latent bugs in compiled-out code (internal cache snoop paths)
============================================================================

All latent because AP040_ENABLE_CACHE=0, but cpu_wrapper.v:257 invites
flipping it back on; fix before anyone accepts that invitation.  These
are precisely the paths with zero test coverage: no bench drives
cache_snoop_stb/s_stb nonzero (tb_ap040_program.v:81 ties it 0).

- 5.1 [BUG] Snoop strobe lost while clkena frozen: snoop_stb_r is a
  single free-running-clk pulse (cpu_wrapper.v:234-245) but the cache
  acts only on ce cycles (ap040_cache.v:122, 309); a chipset write
  landing during a chip-bus wait never invalidates.  Admitted in
  Minimig.sv:422-423.
- 5.2 [BUG] Port-A/B tag-RAM races: a snoop in the last fill-beat cycle
  is undone by C_TAGW's rebuilt valid bits (bram.vhd mixed-port RDW is
  DONT_CARE; ap040_cache.v:255-265); a snoop in the C_TAGW cycle is a
  same-row write/write collision (262 vs 277); a snoop in the rd_accept
  cycle can let C_LOOK hit the just-killed line (252-253, 378-385).
  Same hazard class as the fixed cpu_cache_new fill-tag regression.
- 5.3 [BUG] Port-B arbiter can drop a store invalidate: line-crossing
  store accepted while a snoop wins port B -- the replay cycle serves
  store_inv_lost while winv_pend is cleared as if issued
  (ap040_cache.v:313-320, 329-343, 361-366); the second line's
  invalidate never issues -> stale line after a write-through store.
  store_inv_lost is also a single overwritable entry.
- 5.4 [RISK] Line fill has no berr handling: on berr the adapter aborts
  without mem_ack, the cache re-issues forever while the core has taken
  mem_err and moved on (ap040_cache.v:394-403,
  ap040_bus16_adapter.v:118-131) -- livelock instead of a format $7.
  Unreachable while fills are window-gated to always-acking fast RAM;
  latent for the X2 32-bit fill path.
- 5.5 [RISK] Snoop source coverage if re-enabled: ddram_ctrl exports no
  snoop, so walker U/M writes to page tables in Z3 would not invalidate
  internal D-lines caching descriptors; snoops/stores invalidate only
  the data bank (inv_idx MSB tied 0), so DMA-loaded code leaves stale
  I-lines until CINVA (matches Amiga discipline, weaker than a real
  snooping 040).

Verified OK (cache): CACR is the 040 layout, masked $8000_8000, IE/DE
wired right way round at both consumers; CINV/CPUSH decode (F4xx, cache
field per PRM, scope 00 -> F-line before privilege, supervisor check,
prefetch-queue flush) with the bounded 128-row sweep handshake;
organization is plan-level-2 exactly (split I/D, 4KB, 64x4x16, physical
tags, write-through); reset sweep before serving; MMU/TTR CM ->
c_nocache and mmu_cache_inhibit into all three controllers; the current
build's coherence story is sound (chipset + walker snoop into
cpu_cache_new, the 6f2310e7/959c11d7 fill-tag fix present with its
regression bench); invalidate-on-write instead of update-on-write is
spec-divergent but safe (memory always current); CINV/CPUSH scope
collapse to ALL is safe ONLY while write-through -- it becomes data loss
the day copyback lands.  External-cache CINV completing before the clear
lands (cinv_done tied 1, maintenance toggle accepted cycles later) is
the field-proven legacy TG68K contract, noted not flagged.

## 6. MMU: clean, with two walker-CDC risks that gate X2 work
============================================================================

No outright spec [BUG] in translation, walk, protection, PTEST/PFLUSH or
fault logic.  Architecture: ONE shared module, but per-side resources
match the UM -- banked 128-entry array = a 64-entry 4-way 16-set ATC per
side (ap040_mmu.v:123-140), ITT/DTT split by c_instr, one shared walker
datapath (what X2.7 describes).  Set indexing/tagging match real silicon
exactly (4K: LA[15:12] index, LA16 in tag; 8K: LA[16:13], PA12<=LA12).

### 6.1 [RISK] Walker-CDC ack/ce invariant -- X2.2/X2.4 will break it

ap040_walker_cdc.v:86-91 produces s_ack as a single s_clk pulse; the MMU
samples it only under ce (ap040_mmu.v:336, 227; compat wires
.ce(clkena_in)).  Safe today only because walks happen while the CPU bus
is idle, so ce=1 throughout -- an unstated cross-module invariant.  A
decoupled fetch front end (bus busy during a data-side walk) makes ce=0
cycles possible during a walk: a missed ack permanently hangs the walker.
Must be addressed (latch the ack, or clock the MMU walker interface
free-running) before X2.2's port decoupling or X2.3.

### 6.2 [RISK] Walker-CDC reset asymmetry can desync toggle parity

s_reset_n(cpu_rst) vs m_reset_n(~reset_d) (Minimig.sv:392, 404).  A
CPU-only reset during an in-flight walk can leave parity desynced
(walker_cdc.v:38-52): phantom replay of a stale request (including a
stale descriptor WRITE) or an instant false ack with stale data to the
first post-reboot walk.  Narrow window, silent corruption.

Deliberate simplifications, judged benign: invalid translations never
cached (stricter than UM 3-14/15 -- costs a re-walk per retry of a
nonresident page, buys PFLUSH-free descriptor fixes); U/M writeback is
read-then-write, not locked RMW (single-CPU-master argument holds;
pass_ok blocks all CPU traffic for the whole walk; only DMA into page
tables could lose an update); PTESTW on a write-protected TTR returns
B ($0800) per WinUAE instead of the UM's $0003 -- oracle-sanctioned;
replacement counter increments per fill, not per access (policy is
implementation-defined in effect); U1/U0 cached and reported but drive
nothing (no UPA pins exist in this SoC).

Verified OK highlights: TTR field semantics and TTR0 priority; E-bit
independence; identity default translation; three-level walk index
extraction per UM Fig 3-11 for both page sizes; UDT/PDT decode incl.
indirect-once; WP accumulation; U set on touch, M on write with the
UM 3-13 suppression rule; M-miss re-walk; one-shot fault handshake into
format $7 vector 2 with SSW ATC/MA/LK/RW/SIZE/TT/TM correct; PTEST
forced-walk + MMUSR layout exact per UM Fig 3-6 (incl. LA12->PA12 for
8K); PFLUSH all four variants with G-bit honor and privilege; MMUSR
32-bit at $805; TC/TTR/URP/SRP write masks exact; warm reset clears only
the five E bits and does NOT flush ATCs (UM 3.6.1/3.7.4); walker channel
transfers exactly one transaction per toggle; table-search writes cannot
interleave with CPU writes (pass_ok + epf_pend gates); cache-mode routing
to both the internal cache and all three controllers, with walker writes
snooped so cached descriptors stay coherent.

## 7. Core exception model: remaining notes
============================================================================

- 7.1 [RISK] Double-fault window broader than UM 8.2.1's narrow list:
  in_exc is set for EVERY exception at S_EXC0 (core.v:2443) so a fault
  while stacking a TRAP/interrupt frame, fetching its vector, or
  prefetching its handler halts, where the narrow reading wants a
  recoverable access error.  The UM contradicts itself (7.6.3/1.4 use
  broad wording; 8-7 demands a resident supervisor stack precisely so
  this never happens), so the halting reading is defensible; unreachable
  under a sane OS.  Same for RTE frame-validation faults halting vs UM
  8.4.6.7's frame-below-frame description.
- 7.2 [RISK] RTE to an odd PC stacks the RESTORED SR without forcing S
  (S_RTE_FIN2 core.v:2587-2593); UM 8.4: the address-error frame's SR
  has S set.  The corpus validated popped-SR stacking, but possibly
  never with a USER SR image; directed check recommended.
- 7.3 [RISK] Dead code from the reverted RTE-deferral experiment:
  rte_irq_pend/rte_irq_take_lvl computed and never used (596-604),
  rte_oldsr written and never read -- and the unused wires replicate the
  finding-1.1 hold logic.  Delete or fix in place.
- 7.4 [RISK] t0_special includes TAS (core.v:1058); the UM p.8-9/10 T0

PROVEN AT THE SOURCE 2026-08-20, closing the question.  The generator
and the runtime genuinely contradict each other, and cputest.cpp shows
exactly where:

  * When the traced instruction is followed by more execution, the
    generator does NOT deliver the trace through the vector table at
    all: it records trace_store_pc/sr internally, clears
    SPCFLAG_DOTRACE, and continues (cputest.cpp "trace after NOP",
    the `trace_store_pc == 0xffffffff` block).  The tested exception
    that follows is then converted by the odd-vector rule
    (test_exception >= 4 -> vector 3, stacking original_exception * 4
    -- which also confirms our frame-offset fix from the generator's
    own code).  Expectation: tracecnt = 1, frame names the TESTED
    vector's offset.
  * When the trace is STANDALONE at endpc, the generator raises
    Exception(9), the odd-vector rule applies, and the expectation
    names $24 -- which is why SOME rounds expect vector 9's entry and
    others don't, the per-round variance the bench could never express.
  * The RUNTIME has no such bypass: its trace handler is reached
    through the real vector 9, which main.c itself made odd
    (i >= 4).  The real machine faults fetching vector 9, the good
    vector-3 handler records frame $24 and ends the round, tracecnt
    stays 0.

machine whose trace delivery skips the vector table -- no real 68040
can reproduce that against the runtime's own vector installation.
ODD_EXC 13 + ODD_IRQ 8 are those rounds exactly.  Recorded as
expected-fail; the upstream fix is either exempting vector 9 in
main.c's installer or modelling the vector fetch in the generator's
trace recording.

RTE DID NOT SAMPLE INTERRUPTS (2026-08-20, from hardware) -- the actual
cause of the irq/all failure, and a case where one of our own tests had
enshrined the bug.

cputest enters every test through RTE, which restores SR and redirects
in one step.  ap040_core's S_RTE_FIN2 went straight to S_FETCH and
sampled interrupts nowhere -- unlike fetch_next and go_pc, which both
do.  A request the restored mask unblocks was therefore missed at that
boundary: the target instruction ran and the interrupt arrived one
instruction late, stacking $43900004 where the reference expects
$43900000.  The qualification also has to use the RESTORED mask, since
the sr register still holds the pre-RTE value in that cycle -- the same
stale-mask shape as finding 1.1.

Why it was written that way: test 90/91 asserted the deferral outright,
citing gencpu's `ipl_fetched = 10` for i_RTE.  That marking feeds only
the cycle-exact 68000/68020 paths (check_ipl/check_ipl_next are emitted
under using_ce and isce020()); the 68040 model has no deferral and
checks interrupts in do_specialties once RTE has restored SR and PC.
The same comment also cited "hardware cputest irq/all shows the tested
instruction completing first", which was AP040's own failure being read
as the expected result.  The corpus is explicit the other way: the
ANDSR.B round EXPECTS frame PC $43900000.  Test 90/91 and its rationale
are corrected.

Directed coverage: t_exceptions 151 builds a frame and RTEs into the
target with a settled request, requiring the interrupt AT that boundary
with the target instruction not yet executed; it fails on pre-fix RTL.
151 exists alongside 150 (the MOVE-to-SR boundary) because 150 passed
throughout -- that path always sampled, which is exactly why the first
attempt at this test missed the bug.

IPL RECOGNITION LATENCY (2026-08-20, from hardware).  cputest irq/all
on the board reported an exception-25 frame stacking $43900004 where the
reference expects $43900000 -- the interrupt taken AFTER `andi.b
#0,ccr` instead of before it.  This retracts an earlier call in this
audit: the same signature in the replay harness was written off as a
mid-stream-start artifact, and the board shows it is not.

What is NOT wrong: the boundary logic.  t_exceptions 150 asserts a
request while masked, lets it settle, drops the mask, and requires the
interrupt at THAT boundary with the following instruction not yet
executed.  AP040 passes -- so a settled request is taken at the right
place.

What was wrong: recognition took three cycles.  ipl -> ipl_s1 -> ipl_s2
are the synchroniser, and irq_lvl was a THIRD register stage fed from
them.  cputest times its request (INTERRUPT_CYCLES off SERPER) to land
just before a boundary, and the third cycle pushed it past.  The level
is now taken combinationally from the two synchroniser flops
(irq_lvl_live) whenever they agree, so recognition costs two cycles
instead of three.  The coherence check is unchanged and still guards
against reading a transient encoder value -- 3 -> 5 passing through 7
would otherwise look like an NMI -- and no asynchronous pin enters a
comparison.

Caveat worth keeping: irq/all is calibrated in CYCLES, so it is
sensitive to instruction timing as well as to IPL latency.  Two cycles
is the floor for a synchronised input; if the board still misplaces
this frame, the remaining difference is execution timing rather than
recognition, and chasing it further would mean matching 68040 cycle
counts.

T0 TRACE DOES NOT SURVIVE AN EXCEPTION (2026-08-19) -- found from
HARDWARE, and the most consequential fix here: it was breaking cputest
on the board across whole groups, integer and FP alike.

Symptom the user photographed, twice: `cputest basic/all` on `abcd.b
d0,d0` and `cputest fbasic/all` on `fabs.b d0,fp1`, both reporting

  Exception 4 also pending.
with T0=1 in the test's SR.  The stacked SR of 2000 (T bits clear) is
the tell: the trace was being delivered at the HANDLER's entry, after
exception processing had cleared T -- i.e. AP040's "surviving T0
trace", firing inside cputest's own code after the ILLEGAL that
terminates every test.  Every test in every group ends that way, so
this was mis-reporting the whole corpus on hardware while the sim
replay never saw it.

AP040 armed texc_pend for illegal/privilege/A-line/F-line, reading
WinUAE's Exception_cpu_oldpc as the path every exception takes.  It is
not.  gencpu emits exception_cpu() for exactly five things --
divide-by-zero, CHK, TRAPV, TRAP #n and the RTE format error -- and
Exception_cpu_oldpc then does `if (cpu_model >= 68040 &&
internalexception(nr)) t0 = false`, which covers precisely those
vectors (5, 6, 7, 32-47), with nr == 14 excluded separately.  So on a
68040 activate_trace() is unreachable.  Everything else, op_illg's
Exception(4) included, runs through plain Exception() ->
exception_check_trace(), which ends `regs.t1 = regs.t0 = 0` and only
re-arms for T1 below 68040.  Conclusion: no exception leaves a T0
trace pending on the 040.  The arming is removed.

The texc machinery itself is retained -- it still delivers a trace
that a simultaneous INTERRUPT preempted (fetch_next and go_pc), which
is a different and real case with its own coverage.

Test impact, again cutting against our own work: t_exceptions 109
asserted the survival outright ("one survivor trace + one from the SR
write") and was written from the same misreading.  It now requires the
SR write's trace alone.  The neighbouring CHK case is unchanged --
internal exceptions cancelled the trace before and still do, for a
different reason than the comment claimed.

This is a reminder worth keeping: the sim corpus replay agreed with
AP040 here for months, and only the board disagreed.  Hardware outranks
both the harness and our reading of the oracle.

FPSP ROUTE PRECEDES EA REJECTION (2026-08-19) -- the last of the v24
exception-model findings, and the one that cleared the bulk of them.

On the 040 an FPSP-emulated OPMODE with an illegal EA is still reported
through the unimplemented-INSTRUCTION route (vector 11, format $2, PC
of the following instruction).  AP040 rejected the EA first and emitted
a plain format-$0 F-line.  WinUAE's get_fp_value runs
fault_if_unimplemented_680x0 BEFORE it returns 0 for a Dn or An source,
so `fint.d d0,fp1` takes the FPSP frame while `fabs.d d0,fp1` -- same
malformed EA, hardware opmode -- stays a format-$0 F-line.  AP040 now
carries fp_op_in_hw (mirroring ap040_fpu's op_in_hw) and picks the
route accordingly.  One exception preserved from the source: a PACKED
Dn source returns 0 outright on the 040 without consulting the opmode,
so it stays an F-line either way.

Three consequences fixed with it:
  * the (An)+ / -(An) update stands on the unimplemented-INSTRUCTION
    route too, not just the datatype route (same get_fp_value ordering)
  * a store whose destination cannot hold the format records no FPIAR,
    like the An and PC-relative destinations before it
  * the packed-STORE path leaves (An)+ / -(An) updated as well

(An)+ UPDATE ACROSS A DATATYPE FAULT (2026-08-19) -- second real bug
from the v24 corpus, plus a harness bug that had been hiding it.

RTL: a datatype fault is post-instruction, so the (An)+ / -(An) address
register update STANDS.  AP040's S_FPU_GO unsupp branch performed no
writeback at all, leaving the handler pointed at the operand it had
already consumed.  It now does the same rfw the accepted/done branches
do.  Oracle: WinUAE get_fp_value applies the increment when the EA is
computed (m68k_areg(regs, reg) += sz1[size], 12 for packed) and the
mmufixup undo that could take it back is guarded 68060-only, so on a
68040 it survives the fault.  Directed coverage: t_fpu 323 requires
A3 to advance 12 across a faulting `fmove.x (a3)+,fp1`; it fails in
every phase on pre-fix RTL.

HARNESS: tb_dat_replay sampled the integer register file ONE raw cycle
after S_EXC0 entry.  A write issued by the faulting state has rf_we
high THROUGH that cycle and only reaches the register file on the edge
that ends it, and the sample also has to land on a qualified edge
because the file only commits when ce is high.  The bench therefore
read the pre-write value and reported an architecturally committed
update as missing.  Now deferred two QUALIFIED cycles.  Verified
neutral on its own: with the RTL change reverted and this one kept,
the v20 FPU sweep is back to exactly its 36-slice baseline.

DATATYPE-FAULT STACKED PC FIXED (2026-08-18) -- the first real CPU bug
the v24 corpus found, and it had been invisible by construction.

An unsupported/unimplemented FLOATING-POINT DATA TYPE (packed decimal
in any position, or a denormal/unnormal source) is a POST-instruction
exception: format $3 carrying the FOLLOWING instruction's PC.  AP040
stacked the FAULTING instruction's own PC for source operands
(go_fp_unsupp's non-store branch used pc_i), and pc-2 for a statically
unsupported packed store.  Both are now `pc`.

Evidence, in the order it was weighed: the v24 corpus rejects the old
values outright (it decodes the stacked PC as an oracle where v20
rebuilt those four bytes from the processor's own PC and masked them
out of every comparison -- which is exactly why nothing had
contradicted AP040 before); WinUAE agrees explicitly, fpp.cpp taking
the datatype pend through "simplification: always mid/post-instruction
exception" into newcpu_common.cpp, where vectors 48-55 stack currpc
with format $3 when not pre.  Re-verified against the user's
2026-08-18 upstream WinUAE update: DATA_VERSION, the opcode-tail
phase, the restore_bytes escape, that fpp.cpp path and the 48-55 frame
build are all unchanged.

Note the MC68040UM (9.6.2) reads differently -- it calls opclass
000/010 datatype faults pre-instruction with a format $0 frame.  The
corpus and the emulator agree on format $3 with the following PC, and
AP040 already emitted format $3 (the frame word matched in every
mismatch, only the PC byte differed), so the manual is the outlier
here and the acceptance data wins, per this project's standing rule.

Test impact, recorded because it cuts against our own work: five
t_fpu expectations asserted the OLD PC (tests 76, 81, 236, 239, 255,
plus the section comment).  They were written when the corpus could
not check that field, so they encoded AP040's behaviour rather than
the architecture's.  Updated to the following-instruction PC.

Result: v24 FPU groups 451/562 -> 494/562 (43 slices recovered);
v20 representative gate 6/6; full RTL suite green.

CPUTEST v24 CORPUS ADOPTED (2026-08-18, user-supplied data040.zip).
The harness now reads both corpora, and the long-running "phantom
failure" question is settled by data: FABS.X ([0]),fp3 -- the exact
case photographed failing on hardware, and the one this project chased
across multiple sessions -- PASSES 4/4 on v24.  AP040 was right; the
v20 data was stale.

Porting was four format changes, each verified against WinUAE
cputest sources rather than inferred from the bytes:
  * container: v24 ships one .daz per instruction -- ("\xafMRG", u32
    length, gzip member) records, header first, any non-magic word
    ending the chain (main.c load_file_offset).  Unpacked once into a
    hash-keyed cache under build/cputest/unpacked.
  * header: v24 inserts three longwords after the lvl/mask word, so
    fpu_model and everything after it shift up three and the name moves
    from +80 to +92 (main.c header reader).  Both versions parse.
  * restore_bytes: the escape is keyed on a whole $FF byte followed by
    FULL offset and length bytes, where v20 keyed on the packed length
    field being 31 and carried no offset byte.  Reading it the v20 way
    shifts the opcode image and the CPU executes the fill pattern.
  * exception frame: v24 encodes the STACKED PC as a rel_ordered oracle
    ahead of the frame word.  v20 rebuilt those four bytes from the
    processor's own PC and masked them out of the comparison -- so the
    stacked PC was never checked before and now is.

Two harness bugs fell out of that last point, both invisible under v20:
  * setup patches were emitted grouped by kind (all memory writes, then
    all opcode bytes) instead of in stream order.  v24 setups fill the
    opcode area with $F2 through a CT_PC_BYTES record and then write the
    instruction over it, so grouping let the fill erase the instruction.
  * the NOP/ILLEGAL opcode tail was toggled from the wrong starting
    phase.  The phase is genuinely version-dependent (measured both
    ways): v20 data wants ILLG:NOP, v24 wants NOP:ILLG as current
    cputest does, and forcing either onto the other corpus fails --
    nine v20 slices (FBcc, FDBcc, FMOVEM.X, FSMUL.W) break under the
    v24 phase.  Gated on the header version.

CACHE RE-ENABLE TRIAL (2026-08-18, user-directed: "I need the 68040
cache implemented as BRAM if there's enough left").  Answer: there is
enough AREA and enough BRAM, and there is NOT enough timing slack --
and the blocker is not the cache.

  Area, with AP040_ENABLE_CACHE=1: the design fits at 37,940 / 41,910
  ALMs (91%) and 250 / 553 RAM blocks (45%).  The entity table prices
  ap040_cache at 283 ALMs and +13 M10K: its storage really is block RAM
  by construction (explicit dpram tag row carrying tags+valid+
  round-robin, four inferred cdata ways), so enabling it buys 4KB+4KB
  of cache for a third of a percent of the device.  The 2019-era
  "4226 LABs against 4191" note in cpu_wrapper.v was measured with the
  ATC still in flops and is obsolete.

  Timing: the CPU clock (clk_28, counter[1]) goes from +0.879 ns to
  -4.988 ns (TNS -11.4).  The worst path does NOT traverse the cache:
  it runs ATC dpram -> ap040_mmu -> ap040_core exc_fmt[0], 65 logic
  levels with 59% of the delay in routing.  That cone closes with 2.5%
  of its period to spare in the shipping build, so 283 ALMs of added
  congestion is enough to break it.  Quartus is already at maximum
  effort (HIGH PERFORMANCE EFFORT, PHYSICAL_SYNTHESIS_EFFORT EXTRA,
  register retiming, combo logic), so no build-setting lever remains.

  Value, measured with tb_prof on tests/ap040/asm/bench_loop.s (a new
  loop-and-array benchmark: short inner loop, 256-byte working set,
  self-checking):

                        cache off     cache on
    zero-latency bus     584,894      414,834    1.41x faster
    latent bus           942,404      415,618    2.27x faster

  The second row is the real result: with the internal cache the CPU is
  almost immune to bus latency (+0.2% from adding it), against +61%
  without.  The old blanket claim that ap040_cache "ran SLOWER" holds
  only for straight-line miss-heavy code, which is what the regression
  programs are -- t_integer is 1.36x slower with it on (25,410 vs
  18,742).  Real code spends its time in loops.

  Root cause, then fix (same day).  The cone was read out of TimeQuest
  node by node rather than guessed at: ATC block RAM -> mmu|hit0 ->
  mmu|atc_fault -> cache|pass_active -> core -> 47 levels of
  exc_fmt[2]~NNN priority mux.  ap040_cache was forwarding a BYPASSED
  access straight through in C_IDLE -- pass_active included
  "cst == C_IDLE && c_req", and c_ack is "pass_active ? m_ack : ack_r",
  so c_req (which carries the ATC compare) reached the core's mem_ack
  combinationally, and mem_ack gates 48 exc() sites.  ap040_mmu already
  refuses precisely this shortcut, and says so in its own c_ack
  comment; the cache now follows the same rule: pass_active is
  (cst == C_PASS) alone, and a bypassed access is issued from C_PASS.

  Result with AP040_ENABLE_CACHE=1 and that one change: the design is
  timing-CLEAN for the first time this session.  clk_28 +0.844 (from
  -4.988), clk_114 +0.132 -- which also retires the pre-existing
  -0.145 violation in the legacy cpu_cache_new dtram -> cpu_ack path --
  pll_hdmi +0.093, hold +0.246, recovery +3.359, and no
  "Timing requirements not met" warning at all.  37,962 ALMs (91%),
  250 RAM blocks (45%).

  Cost of the extra cycle: bypassed accesses only (I/O, misaligned,
  cache-inhibited); cacheable traffic goes through C_LOOK untouched.
  Measured at 0.02% on bench_loop (414,904 vs 414,834 cycles) and
  0.35% on t_integer (25,500 vs 25,410).  Full suite green, cache
  snoop bench T1-T5 green, corpus gate 6/6.

5.4 FIXED (2026-08-18) -- the last blocker to re-enabling the
internal caches.  ap040_cache had no bus-error input at all: on a fill
beat that faulted, the adapter dropped the cycle without m_ack and the
cache sat in C_FILL re-issuing the same address forever while the core
had already taken the fault and moved on -- livelock, not a format $7.
The cache now takes m_err (wired to the same berr the core and the
adapter see) and abandons the transfer: C_FILL drops r_issued and
returns to C_IDLE WITHOUT reaching C_TAGW, so the partly-filled line is
never validated and its beats are unreachable; C_PASS releases the bus
the same way but still honours an owed second-set invalidate (more
invalidation is always safe under write-through); and a new err_hold
flag refuses to re-accept the still-level-held request until the core
withdraws it, which would otherwise re-issue the faulting address on
the next cycle.  Directed coverage: tb_ap040_cache_snoop T5 sweeps the
error across all four fill beats plus a faulting write-through store,
requiring the bus to go idle, the cache to keep serving (the exception
handler's own accesses), and the abandoned line to refetch changed
memory.  Pre-fix (port present, abort logic absent) the bench wedges:
CINV never completes and reads return the abandoned fill's data --
12 failures against 0 after.

FADD.W / FINTRZ.X / FMOVE.L SEQUENCE AUDIT (2026-08-20, from a hardware
report of D6 ending up off by one and reaching $7FFFFFFF).  AP040 is
correct at every step it is responsible for; the break in the chain is
architectural, not a defect:

  * FADD.W #1,FPn is hardware and exact -- extended carries a 64-bit
    mantissa, so +1 stays exact far past 2^31.
  * FINTRZ.X is NOT a hardware instruction on the 68040 (nor is FINT).
    op_in_hw excludes opmodes $01/$03, so it takes the unimplemented-FP
    trap and the FPSP must emulate it.  Verified frame: vector 11,
    format $2, stacked PC = the FOLLOWING instruction.  This is the one
    step whose RESULT AP040 does not compute.
  * FMOVE.L FPn,Dn is hardware and uses the FPCR ROUNDING MODE, not
    truncation: 2.5 -> 2, 2.6 -> 3.  Anything >= 2^31 saturates to
    exactly $7FFFFFFF with OPERR.  Results verified identical to qemu
    on nine probes across the 2^31 boundary.

  So the reported off-by-one is what the sequence does when FINTRZ does
  not take effect: without the truncation, FMOVE.L ROUNDS, and once the
  value passes 2147483647.5 it saturates to $7FFFFFFF -- which, used as
  a BLE loop bound, is the unterminatable loop audited above.

  Two places AP040 is MORE correct than qemu, both confirmed against
  softfloat's floatx80_to_int32 SOFTFLOAT_68K path:
    - NaN to integer returns the NaN's HIGH MANTISSA LONGWORD
      ((int32)(a.low>>32)), not $7FFFFFFF: AP040 returns FFFFFFFF and
      C0000000 for the two probes and matches the reference exactly,
      while qemu returns $7FFFFFFF for both.
    - AP040 raises OPERR on out-of-range and NaN conversions and INEX2
      on inexact ones; qemu raises neither.
  A denormal source correctly takes vector 55 on AP040 (unsupported
  data type, FPSP territory on real silicon); qemu computes it.

  COVERAGE GAP FOUND: the v24 corpus ships 4_FINT EMPTY (lmem.dat and
  tmem.dat only, no slices), so the group name promising FINT/FINTRZ
  coverage delivers none.  The real coverage is in PackedFPU --
  FINT.* and FINTRZ.*, 28 slices, all passing.  Probes preserved as
  tests/ap040/hw/fp_to_int.s and hw/fp_to_int_nan.s.

  * MMUSR assembly is bit-identical to WinUAE's.  WinUAE builds
    status = phys | (desc & (G|Ux|S|CM|M|W|R)); AP040 assembles the same
    bits in the same positions ([10] G, [9:8] U1/U0, [7] S, [6:5] CM,
    [4] M, [2] W, [0] R) with the page address above them.
  * Write protection accumulates across table levels on both sides:

UNDERFLOW UNDER DIRECTED ROUNDING FIXED (2026-08-20).  The FPU-vs-WinUAE
differential above found one real numerical defect inside the underflow
class it had otherwise classified as architectural: when the significand
shifted out entirely (extra > 66), F_ROUND flushed to zero for EVERY
rounding mode.  That is correct for round-to-nearest and round-to-zero,
but a DIRECTED mode pointing away from zero must round a nonzero value up
to the smallest representable magnitude -- IEEE requires it and
softfloat's roundAndPackFloatx80 does it.  Returning zero there is a
sign-dependent wrong answer, not an encoding difference.

Fixed for single and double rounding precision, where the smallest
magnitude at emin is still a normal extended number: one unit in the last
place of the narrowed significand ($0000_0100_0000_0000 single,
$0000_0000_0000_0800 double) at the precision's minimum exponent.
Verified against WinUAE directly -- 2^-3637 + itself at single precision
with round-to-plus now yields 3F81 00000100 00000000 on AP040, which is
byte-for-byte what floatx80_add produces.

EXTENDED precision keeps flushing to zero and is now the only remaining
member of the class: representing it needs the true denormal encoding
(exponent field 0) and a signed working exponent, which this
implementation does not carry.  Recorded rather than silently left in the
"architectural" bucket.

Regression: directed suite green, full v24 corpus 3776/3801 with the
failing set IDENTICAL to before the change (the four generator
operand-placement slices and the 21 ODD_EXC/ODD_IRQ trace-model rounds),
and the FP differential is now 25/25 seeds clean.

UNIMPLEMENTED-INSTRUCTION FRAME SET E1 (2026-08-20).  Chasing the AIBB
MFLOPS hang -- whose only plausible mechanism was an FPSP that never
advances -- the FSAVE $41/$30 frame AP040 hands the FPSP for an
unimplemented instruction was compared FIELD BY FIELD against the
frame WinUAE builds, not just in shape.  Everything matched except one
bit:

  capture_unimp set fstate_flags = 3'b100, i.e. E1 = 1.

E1/E3/T are the ARITHMETIC exception-pending bits.  WinUAE sets them in
fpsr_check_arithmetic_exception (the e1 and e3 classes) and, for a
packed operand, in fp_unimp_datatype; fp_unimp_instruction sets NONE of
them and leaves reset_fsave_data's zeros in place.  The frame for an
unimplemented instruction carries the instruction in CMDREG1B and its
operand in ETEMP -- there is no pending arithmetic exception for the
handler to complete, and claiming one points the FPSP's dispatch at the
arithmetic path instead of the emulate-and-advance path.  That is
exactly the shape of a handler that returns without advancing, i.e. an
instruction that retraps forever.

Verified for FINTRZ.X FP6,FP0 -- the middle instruction of the reported
FADD.W/FINTRZ.X/FMOVE.L sequence -- by capturing the real frame from
the RTL through FSAVE and decoding every field against WinUAE's writer:
frame id $41300000, CMDREG3B $0003 (matching the documented
(extra & $3C3) | ((extra & $038) >> 1) | ((extra & $004) << 3) mapping
of extra = $1803), CMDREG1B $1803, STAG 0, DTAG 0, FPTEMP and ETEMP
both the operand.  Only the flags word differed.

Fixed to 3'b000.  t_fpu test 266 asserted $04000000 for fsin.x fp0 and
was encoding the RTL's error rather than checking it -- corrected with
the reasoning inline, the same failure mode as tests 76/81/90/91/100/
109/236/239/255 and the odd-target exp_pc sites.  Test 309, which
checks E1 on the ARITHMETIC e1 frame (enabled SNAN from a released
load), is untouched: E1 = 1 is correct there.

Regression: directed suite green, full v24 corpus 3776/3801 with the
failing set unchanged.  The corpus cannot see this bit (cputest never
FSAVEs an unimplemented instruction), which is why it survived every
previous sweep -- and why hardware, not simulation, is what settles
whether it was the hang.

CONFIRMED ON HARDWARE (2026-08-20): the E1 fix was the AIBB MFLOPS hang.
The user reports MFLOPS now runs on the 20:56 image.  That promotes the
E1 finding from "verified spec divergence, plausible cause" to the
proven mechanism, and it retroactively explains the whole chain of
symptoms reported across this investigation, which had looked like
three separate problems:

  1. FINTRZ.X is not a hardware instruction on the 68040 (op_in_hw
     excludes opmodes $01/$03, exactly as WinUAE's
     fault_if_unimplemented_680x0 does), so it traps to the FPSP.
  2. AP040's frame claimed E1 = 1, i.e. "an arithmetic exception is
     pending, its operand is in ETEMP".  The FPSP dispatched down the
     arithmetic path instead of emulate-and-advance, and FP0 never
     received the truncated value.
  3. FMOVE.L FPn,Dn then converted whatever FP0 actually held using the
     FPCR ROUNDING MODE -- round-to-nearest, not truncation, which is
     precisely why the code called FINTRZ first.  Past 2147483647.5
     that saturates to $7FFFFFFF with OPERR, which is correct behavior
     for the value it was given.
  4. $7FFFFFFF as the bound of `cmp.l d6,d7 / ble.b loop` is an
     architecturally unterminatable loop: nothing is signed-greater
     than MAXINT, so BLE is taken for every D7, forever.  The reported
     D7 = $80698873, ~6.9 million iterations past the wrap, is that
     loop still running.

  So CMP.L and BLE.B were never broken -- they were fed a poisoned
  bound.  The off-by-one and the "hang" were the same defect seen at
  two removes from its cause, and the cause was one bit in a frame the
  corpus structurally cannot inspect.

  Lesson recorded for the class: cputest can only see what it executes
  and compares.  It never FSAVEs an unimplemented instruction, so no
  amount of corpus sweeping could have found this.  The finding came
  from decoding a real frame out of the RTL and diffing it field by
  field against WinUAE's writer -- the same "execute the oracle, do not
  read it" discipline the FP and MMU differentials now enforce.
