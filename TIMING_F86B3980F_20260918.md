# Timing diagnosis: f86b3980f, 2026-09-18

**The loaded image fails timing and is not a measurement platform.**
Pointer artifacts and performance observed on it cannot be used to assign
a CPU logic cause or validate a fix. Recover timing before further board
comparisons. This is a confirmed build failure, not merely an unmeasured
risk. Its exact contribution to a particular artifact is still unknown.

Loaded image confirmed by the user:
`Minimig-ap040-40mhz-f86b3980f-20260918_152411-TIMING-FAIL-DO-NOT-FLASH.rbf`.

## Separate the two emu clocks

`build.sh` labels the minimum across **all emu clocks** as "emu (CPU)".
That label does not identify an individual CPU execution path. Production
connects PLL output 0 to `clk_114` and output 1 to `clk_sys`; the CPU
wrapper runs on `clk_sys`, and the SDRAM controller runs on `clk_114`.

Worst setup slack across the four reported corners:

| Clock / build gate | ec25690cd | f86b3980f | Difference |
|---|---:|---:|---:|
| `emu` output 0, `clk_114` / SDRAM | +0.132 ns | **-1.253 ns** | -1.385 ns |
| `emu` output 1, `clk_sys` / CPU wrapper | +0.625 ns | +0.460 ns | -0.165 ns |
| HDMI | -0.345 ns | **-0.667 ns** | -0.322 ns |

The earlier `33e173e22` emu-group minimum was +0.476 ns. Thus the campaign
comparison +0.476 -> +0.132 -> -1.253 is valid, but calling its last step
an increase in the CPU's combinational path depth is not established.
`ec25690cd` passed the emu gate; its negative HDMI slack means it was not
fully timing-closed for the scaler output.

Sources: `build_ap040-40mhz_20260918_121123.log` and
`build_ap040-40mhz_20260918_152411.log`. The latter's slow 100C table is
at line 3418. The positive CPU-clock result does not make the machine
usable: the failing memory/chipset domain is part of the system.

## What the failing path actually contains

The retained [TimeQuest report](tests/ap040/audit_evidence/f86b3980f_setup_top10.rpt)
comes from the completed f86 fit, not a new compile. Worst setup path:

`ram1|sdata_reg[11]` -> `ram1|walker_sdata_pipe0[11]`

| Property | Reported value |
|---|---:|
| Setup relationship | 8.808 ns |
| Slack | **-1.253 ns** |
| Logic levels | **1** |
| Data delay | 8.317 ns |
| Interconnect contribution | **7.225 ns (87%)** |
| Cell contribution | 1.092 ns |
| Clock skew | **-1.414 ns** |

The direct failing data path is an SDRAM input-register hop, not the core
write-probe or MMU permission cone. The report also contains
`sdata_reg[11] -> sdata_chip[11]` at **-0.315 ns**, SDRAM output-enable
paths as low as -0.476 ns, and chipset-to-SDRAM address paths as low as
-0.053 ns. Fixing only the worst endpoint does not establish closure.

Between `ec25690cd` and `f86b3980f`, the changed production files are the
core, MMU and compat wrapper. `sdram_ctrl.v`, `cpu_wrapper.v`, `Minimig.sv`,
`Minimig.qsf` and `Minimig.sdc` are unchanged. Source changes elsewhere can
alter placement/routing of an unchanged block; this is compatible with
deterministic fitting for each source/netlist.

The 1.385 ns difference is a difference between worst slacks, not a measured
increase in delay along a matched pair of paths. A previously observed
0.344 ns source-to-source swing is not an upper bound on placement effects.
The current path's routing/skew statistics contradict treating magnitude
alone as proof of extra combinational depth. Conversely, unchanged SDRAM
RTL does not exonerate the write probe: it could have changed global fit
pressure or placement. Its causal role remains unisolated, and several RTL
commits separate the two builds.

## Recovery target

Prioritize the SDRAM input-register fanout, placement and first capture
stage, together with the other reported negative SDRAM paths. The source
already documents that adding stages *after* a long first hop does not
shorten that hop (`sdram_ctrl.v:559`). Its synchronous reset mux and physical
placement are concrete candidates to inspect, not yet validated fixes.

A next candidate should state which reported path it changes and how,
preserve walker/chipset data alignment, and pass the relevant memory
regressions before a single source-specific timing build. Do not relax
constraints or discard the partial-write correctness fix based solely on
the slack difference. HDMI closure also matters before interpreting scaler
artifacts. No additional core audit is needed to justify this priority.

No production RTL, constraints, or fitter settings were changed for this
diagnosis. No Quartus process was started and no image was flashed.
Timing recovery has **not** yet been achieved.

## Recovery candidate: shared input capture and registered write select

The next source changes only `rtl/sdram_ctrl.v` in production. It retains
the core/MMU write-probe fixes, Fast RAM caching, clock constraints, and
fitter settings. Source manifest ID:
`1b2bd22e31dfe59971c57266e81bced49db47a27278ac25496ebbca27bd1efe0`.
This is an **uncommitted patch over `28d1101b2`**, not that clean commit.

* The cache, chipset and walker share `sdata_reg_q` as their first SDRAM
  input capture. The walker no longer has a separate resettable first
  capture with a LUT in front of it. A one-bit delayed `reset_n` recreates
  the original reset value at the next, internal stage. This preserves
  the three-stage walker latency, including the first cycle after reset.
* `cas_write_go` registers the entire ordinary-write qualifier one cycle
  before the data-pin enable and WE consume it. It uses the next value of
  `init_done`, including reset and slot resynchronization, so that the
  registered decision agrees with the original expression at the pin edge.
  The separate second walker write remains at the original state.

The candidate passed these pre-build checks:

* Nine controller comparisons against `f86b3980f`: **380,097 cycles** with
  identical public outputs and data-pin enables. Each run covers all six
  slot types, chip and walker reads/writes, reset at all sixteen slot phases,
  and sixteen slot-clock phase changes. Three deterministic seeds run with
  the outer cache enabled, enabled with READ_PIPE=1, and disabled.
* **13/13** SDRAM/dualram FPU and MMU program executions, including CPU phase
  changes, outer-cache bypass and READ_PIPE=1. These use memory models and
  self-checking programs; the cycle-comparison bench instead uses a varying
  external input pattern and does not itself model SDRAM transactions.
* **8/8** chipset burst/control legs (`sdram32` and `sdram32_rp1`), including
  five expected-failure controls for wiring/phase errors.

The controller comparison is bounded simulation, not a formal proof.
The new runner is `tests/ap040/check_sdram_timing_equivalence.py` and the
simulation adapter supports both the old and registered write expressions.
The retained [test results](tests/ap040/audit_evidence/sdram_timing_checks_20260918.json),
[source manifest](tests/ap040/audit_evidence/sdram_timing_source_20260918.json),
and [production patch](tests/ap040/audit_evidence/sdram_timing_candidate_20260918.patch)
identify this candidate independently of the build script's HEAD-based name.
Raw logs and the exact source manifest/patch are under
`scratchpad/timing-recovery-20260918/`. The first test attempt exhausted

## Candidate result: emu closes, full closure remains outstanding

One source compile completed at 19:14:32 in 16m14s. Worst slacks across
all four reported corners, in nanoseconds:

| Clock | f86 setup | Candidate setup | Candidate hold |
|---|---:|---:|---:|
| SDRAM / emu output 0 | -1.253 | **+0.015** | +0.071 |
| CPU / emu output 1 | +0.460 | **+0.322** | +0.090 |
| HDMI | -0.667 | **-0.093** | +0.122 |

The candidate passes the existing emu gate for setup, hold, recovery,
removal and minimum pulse width. **It does not close HDMI timing**, and
15 ps of SDRAM setup headroom is substantially below the last validated
`ec25690cd` image's 132 ps. This is progress, not a fully timing-closed
replacement or an artifact-cause result. No further build was launched.

Detailed paths from this completed fit identify the next limits:

* [First input capture](tests/ap040/audit_evidence/sdram_recovery_input_capture_20260918.rpt):
  worst `sdata_reg -> sdata_reg_q` setup is **+1.615 ns** at slow 100C.
  The resettable `walker_sdata_pipe0` endpoint was removed. The old first-hop
  failure is no longer the limiter; the first capture remains in the same
  logical cycle as before.
* [SDRAM clock](tests/ap040/audit_evidence/sdram_recovery_setup_20260918.rpt):
  `agnus_beamcounter|hpos[1] -> ram1|sd_addr[12]` is now worst at **+0.015 ns**.
  It crosses from the CPU clock into the SDRAM clock with a 17.616 ns
  relationship. More margin requires work on the chipset-address path.
* [CPU clock](tests/ap040/audit_evidence/sdram_recovery_cpu_setup_20260918.rpt):
  `ram2|cpu_cache|cpu_ack -> core|g_fpu.fpu|b_e[9]` is worst at **+0.322 ns**.
* [HDMI, slow -40C](tests/ap040/audit_evidence/sdram_recovery_hdmi_cold_20260918.rpt):
  `ascal|o_h_poly_t.r0[18] -> ascal|o_h_poly_pix.r[0]` is worst at **-0.093 ns**.
  The scaler has positive worst setup at slow 100C (+0.050 ns), which alone
